# Next horizon brief — horizon 28 (after horizon 27: staged Pending Change Set for the flag-edit surface)

## Recommended scope
Keep horizon 28 roughly the size of horizon 27 — one coherent extension of the staged model, not a sweep. The highest-value shape is converting a small, homogeneous group of Write Surfaces that the accumulated-snapshot representation already covers (rollout, attach-segment, and create-flag are all flag-snapshot folds through applyFlagEdit) so the Pending Change Set is proven over more than one surface while its representation stays unchanged; the surfaces that are NOT snapshot folds (rollback, deletes, segment CSV upload) should stay out, since they force the representation decision and would blow the horizon up. Expect the real work to be less about new use cases than about the echo discipline — every form losslessly carrying the payload, the frozen Base Version not leaking into surfaces that should stay immediate, and the exact-HTML view tests absorbing the added hidden inputs. If the payload-size or multi-page-persistence research comes back badly, the honest alternative is a smaller horizon that answers only the representation/persistence question with a spike plus one surface, rather than three. Either way, leave the modal-dialog migration, the environment-page.ts/http-server.test.ts splits and the open blockers out; taking any of them alongside surface conversion is what makes this horizon too big.

## Unknowns
- Once the other seven Write Surfaces are converted, does a single Pending Change Set span flags AND segments, or does each kind of write get its own set — and can a set mix a flag edit with a segment CSV upload (which uses a higher body limit than the 1 MiB features-route cap)?
- What is the actual serialized byte cost of the accumulated-snapshot payload for a realistic production-size snapshot, echoed on ~9 forms per render, and at what snapshot size does the 1 MiB readForm cap make hidden-field carriage unworkable?
- If every surface becomes staged, does replayOnLatest/canReplayEdit in edit-feature.ts have any remaining caller — i.e. is the auto-replay machinery (and the changes-dialog merge UI wired to it in app.js) deletable, or does it still serve the update-watch poll path?
- Does the operator need a Pending Change Set to survive navigation between pages (versions page, segments page, another environment) — because hidden-field carriage only holds within the forms of one rendered page, and multi-surface staging almost certainly crosses pages?
- Can a Pending Change Set be built by non-flag writes whose result is NOT expressible as an accumulated snapshot JSON (rollback, deletes, segment publishes go through different writers), and if so what representation replaces the accumulated-snapshot trick chosen in horizon 27?
- What does the Review Dialog show when the drift warning fires after horizon 27 ships — does publish-anyway on a multi-surface set need per-flag conflict granularity, or is the whole-set override still acceptable?
- Did horizon 27's frozen-Base-Version change to renderFlags's context object leak into the seven immediate-publish forms, i.e. do those forms now post a stale baseVersion and get spurious 422s while a set is open?

## Decisions needed
- Whether the next horizon converts more Write Surfaces to staging or instead moves the settled edit surface's markup into a modal dialog — the two deferred tracks conflict, since converting surfaces churns markup the dialog move would redo.
- Whether a Pending Change Set stays page-scoped hidden-field carriage or must gain a persistence mechanism (server state, storage, or an S3/disk draft object) once staging spans multiple pages — the horizon-26 storage decision was scoped to one surface and multi-surface staging reopens it.
- Whether the Pending Change Set's representation stays "accumulated snapshot JSON" or becomes a heterogeneous operation list, forced by surfaces (rollback, deletes, segment writes) that are not a flag-snapshot fold.
- Whether the seven immediate-publish surfaces are converted all at once or incrementally, and — if incrementally — what the page does when a staged set is open and an immediate surface is submitted (block, publish anyway, or auto-stage).
- Whether replayOnLatest/canReplayEdit and the changes-dialog merge UI get removed, kept as the immediate-path fallback, or replaced by the drift warn-and-choose path everywhere.
- Whether to accept environment-page.ts and http-server.test.ts growing further, or to take the deferred split first as an enabling step before adding more staged surfaces.
