# Next horizon brief — horizon 27 (after horizon 26: full-width page shell, Side Menu, first Modal Dialogs, Confirmation Dialogs)

## Recommended scope
Horizon 27 should be the staged pending-changes write model and essentially nothing else — it is a change to how every dashboard write reaches S3, touching the application layer, the HTTP routes, five write surfaces across three pages, the unit suite and the e2e suite, and it opens the one genuinely undecided architectural question in this project (where a draft lives in a server with no state). Realistically that means an early, explicit decision phase or spike on draft storage and draft representation, then a thin vertical slice that stages exactly one write surface (the new-flag or edit-flag form is the natural candidate) end to end through the review dialog and a single Update publish, with the version-drift warn-and-choose path proved by a Playwright spec, before converting the remaining surfaces. Do not also take the remaining dialog-migration phases, the environment-page.ts split, the http-server.test.ts split, the /env/<env>/flags route or the blockers backlog — any of those can be sequenced after the write model settles, and several of them would have to be redone if the write model changes their markup. If the drift decision or the storage decision turns out to need operator input, surfacing that early is more valuable than shipping more surfaces.

## Binding decisions from horizon 26 — do NOT re-open
- The operator has ALREADY DECIDED the version-drift rule for the pending draft: the draft is kept against the version it started from; if the environment's current version moves underneath it, the review dialog WARNS at review time and lets the operator publish anyway or discard. It never hard-blocks and never silently auto-replays.
- The Side Menu selects a view by ROUTE, never by a new query-string key; the url-state vocabulary stays filter/open/page/pageSize.
- The per-flag row "Expand" disclosure stays a disclosure bound to the URL contract — it does not become a dialog. Only panels nested inside a row move into dialogs.
- Every dialog keeps the no-JavaScript fallback: without scripting it renders as an inline card whose form submits normally.
- Server-side guards are untouched by any UI confirmation work: the same-origin POST guard, expectedCurrentVersion CAS and validation stay exactly as they are.

## Unknowns
- Where does a pending draft physically live between two HTTP requests, given the dashboard is a stateless 127.0.0.1 node:http server with no store and no session concept — an in-process module-level map keyed by environment, a hidden form field carrying the accumulated snapshot JSON forward on every request (the way the publish dialog's draft textarea already round-trips), browser storage in the uncovered app.js, or a new S3/disk-backed draft object?
- How is a pending draft expressed: as an accumulated full snapshot JSON document (which is exactly what mergeDraft and snapshot-diff already consume), or as an ordered list of FlagEdit operations replayed at publish time? The existing FlagEdit union and applyFlagEdit make the second plausible, but nothing in the repo stores an edit list today.
- If the draft lives in server process memory, what is its lifetime and identity — one draft per environment for the single local operator, or per browser tab? What clears it (publish, discard, server restart), and does a restart losing an operator's unpublished work count as acceptable?
- Does the existing snapshot-diff / changes-dialog fragment pair actually answer "review pending changes" (draft vs base), or does it only answer "what changed upstream" (base vs latest)? If both views are needed in one dialog, is that one fragment endpoint with a mode or two?
- What happens to the CAS expected-current-version check once writes no longer publish per form submit — does the single Update publish still send expectedCurrentVersion equal to the version the draft started from (so a drifted environment gets a conflict the warn-and-publish-anyway path must then override), or does publish-anyway switch to an unconditional or replay-on-latest write? These are different S3 semantics and the decided no-auto-replay rule constrains but does not settle it.
- When a single edit is staged rather than published, what does the server now validate and when — is a 400/422 still returned inline at stage time (so an invalid draft can never enter the pending set), or is validation deferred to the Update click where several accumulated edits could fail at once?
- Do the five write surfaces move to staged writes all at once, or can some (e.g. segment upload, which publishes a separate S3 segment object, not a snapshot version) stay immediate? Segment publishing has its own pointer and its own CAS and may not belong in the snapshot pending draft at all.
- Is rollback a staged change or an immediate publish? It writes a new version from an old one and does not fit the accumulated-edits model.
- How much of the staged-write behaviour can be proven by unit test at 100% coverage if any part of the draft lives in app.js, and is that acceptable, or does the still-unwritten standing rule about app.js logic (an open blockers.md entry) have to be decided first?
- Which of the four remaining Write Form surfaces (edit-flag + Edit rules, rollout, attach-segment, create-segment) should move into Modal Dialogs before vs. after the write model changes, given a staged-write rewrite may change their markup anyway?

## Decisions needed
- Where the pending draft is stored: server process memory, a hidden form field carried per request, browser storage, or a persisted object. This is the horizon's central architectural choice and every other question resolves after it.
- Whether the draft is an accumulated snapshot document or an ordered list of FlagEdit operations.
- Whether "review pending changes" reuses the existing changes/merge fragment + shared dialog shell, or gets its own dialog and its own diff renderer.
- What expectedCurrentVersion the single Update publish sends, and what "publish anyway" after a drift warning means at the S3 layer (override CAS vs publish against latest) — consistent with the already-decided no-auto-replay rule.
- Whether per-form validation stays synchronous at stage time (400/422 inline as today) or moves to the Update click.
- Which write surfaces are in the staged model: the four snapshot-editing forms only, or also segment upload, rollback and the destructive actions.
- Whether an unpublished draft surviving a server restart is required, which alone forces or rules out in-memory storage.
- Whether any pending-draft logic may live in app.js given it is permanently outside the coverage gate — i.e. whether this horizon must finally settle the standing app.js rule.
- Whether a confirmation is also added before the rollback action on the versions page (deferred from horizon 26: rollback is arguably destructive but the operator's complaint enumerated deletes).

## Research
- Read packages/dashboard/src/application/merge-draft.ts end to end plus packages/dashboard/src/domain/snapshot-merge.ts and snapshot-diff.ts — the DraftMerge type ('invalid-draft' | 'unavailable' | 'ready' with from/to/entries) is the closest existing thing to a pending-draft model and decides whether the review dialog can reuse it or needs a new one.
- Read packages/dashboard/src/infrastructure/views/changes-dialog.ts and merge-dialog.ts together with the app.js fetch that injects them into #changes-body: confirm these are inner-HTML fragment renderers, not dialogs, and judge whether "review pending changes" is a third fragment on that same reusable dialog shell or a dialog of its own.
- Read the GET /env/<env>/changes and GET|POST /env/<env>/merge and POST /env/<env>/merge/apply handlers in http-server.ts — they are the only existing routes that read a draft, and they show exactly how the draft reaches the server today (form field vs stored).
- Read packages/dashboard/src/application/edit-feature.ts (its expectedCurrentVersion, replayOnLatest and canReplayEdit logic) and publish-snapshot.ts — the pending-draft publish path must either reuse or deliberately bypass them, and the never-auto-replays rule interacts directly with replayOnLatest.
- Read packages/dashboard/src/domain/flag-edit.ts: the FlagEdit union and applyFlagEdit are what an accumulated edit list would be made of, and both edit-feature switches are exhaustive, so any new staged-edit kind ripples there.
- Re-read the publish dialog draft round-trip in views/environment-page.ts (the state.draft !== undefined && conflict === undefined open-on-load condition and the snapshot textarea) — it is a working precedent for carrying a whole draft snapshot through the request cycle with no server state.
- Read views/state-fields.ts and url-state.ts: every staged write form must keep both URL-state mechanisms (withUrlState action + hidden stateInputs), and the planner should decide whether a pending-draft identifier is a new url-state key or deliberately not.
- Re-read blockers.md, specifically the 200+422 concurrent-replay race, the pointer-read timing window, and the undecided standing rule for how much logic may live in the uncovered app.js — the last one blocks any client-side-draft option.
- Read whichever dialog/confirmation modules horizon 26 actually shipped (modal-dialog.ts, dialog.css, side-menu.ts) rather than assuming the planned shape — the kept-phase list is a plan, not a record.
